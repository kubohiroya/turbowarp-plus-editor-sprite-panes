# TurboWarp Plus Editor Sprite Panes

[日本語](README.ja.md)

The panes inside a sprite or stage editing tab of TurboWarp Plus Editor. Each pane is a React component that receives the selected target's data and reports edits through callbacks. Arranging the panes into tabs and splits is the job of `@kubohiroya/turbowarp-plus-editor-layout`.

## Panes

| Export | Role |
| --- | --- |
| `./sprite-asset-pane` | `SpriteAssetPane` previews costumes or sounds and keeps the selection while the pane is inactive. In the variables section it lists variables, commits a value edit once, and opens a Scratch-style dialog to create, rename or delete a variable. `NativeAssetPanel` hosts the GUI's own asset list |
| `./sprite-message-pane` | `SpriteMessagePane` draws, on a Sent tab and a Received tab, a diagram of the messages the target sends or receives. Each sender shows the hats of the scripts that send, which open their blocks. A message without receivers or senders carries a warning at the empty end. A message is renamed in a dialog opened from the menu of the ▼ after its name in the diagram |
| `./sprite-function-pane` | `SpriteFunctionPane` lists the functions of a sprite or the stage — its custom block definitions and the named functions of the named-functions extension (`kubohiroyanamedfunctions`, or another extension ID passed to `readTargetFunctions`) — as a list, ordered by name, in Z order (rows) or in N order (columns), or as a call graph that flows left to right (LR) or top to bottom (TD), with its direction controlled by the host through its section rail; the graph places functions by who calls whom, so only the list has an order to pick. Like the code area, the graph pans by dragging or with the wheel, zooms with the − + = buttons or Ctrl + wheel, and shows a minimap; hovering or focusing a function highlights the links into and out of it and the functions at their other ends. Given a `view`, it shows only one of them, as when each is a section of its own, and the list also shows the other hat scripts the host passes in `hats`, with the drawing of each hat it passes in `thumbnail`, which open through `onOpenScript`. Named functions gather in a section of their own below the standard ones. Functions carry an f(x) mark, and the item the host names in `selectedId` is highlighted. A function's use count opens a dialog of the blocks that call it (`uses`, which `readTargetFunctions` reads); picking one opens its script with `{block}`, so the host can show that block. A function picked in either opens through the host's `onOpenFunction`, such as in a tab beside the pane, or in a dialog without it. Given the project's `others` targets, `readTargetFunctions` also reads into `globals` the global named functions (for all sprites) defined elsewhere that this target's functions call or that call this target's global functions; the graph draws every global function grey with white text, names the sprite or stage that defines one from elsewhere (the host opens it with its owner metadata), and the list leaves them out. The graph sets functions that call none and that none calls apart, in rows below the others. Given the host's `onCreate`, an “Add a new function” button sits below the list and in the bottom left corner of the graph (without functions the graph is still drawn, blank, with a notice in its middle pointing to that button, and the list points to the one below it); it asks for a name and a kind (a standard custom block or a TurboWarp-Plus named function, starting from the kind used last) in a dialog, makes the function with `onCreate(kind, name)`, and opens and selects it. The dialog gives the host an element to mount an editor of that definition script; `readTargetFunctions` reads the definitions from a VM target |
| `./sprite-properties` | `SpritePropertiesPanel` is the properties form. It reflows with the pane width, rejects stale edits when the selected sprite changes, and applies updates to the VM. `createSpriteInfoAdapter` connects it to the GUI's sprite info |
| `./sprite-editor-toolbar` | `SpriteEditorToolbar` is the vertical rail that switches between Free layout (the code area), Hats and functions, and Calls; Costumes or Backdrops and Sounds; and Variables and Messages, with a line between the three groups and a search box for the active section |
| `./temporary-variables` | `readTemporaryVariables` collects the variables of the Temporary Variables extension (`lmsTempVars2`) that the code names with fixed text: thread variables, and on the stage also runtime variables, with their read and write counts and the functions (custom blocks) that set them. For runtime variables it also collects, across sprites, the functions that read them and the functions that change or delete them. While the debugger has paused the project, it adds the values at that moment, including variables whose names are built at run time. `watchTemporaryVariables` reports pauses, resumes and value changes during a pause. `SpriteAssetPane` lists them as Thread Variables and Runtime Variables after the sprite or global variables, with a badge counting the functions in the Read in and Changed in columns of runtime variables. An extension that has `getInspectorVariables()` (`runtime.ext_<id>`, `InspectorVariableProvider`) can list its own variables, which are not Scratch variables (such as the story variables of TurboWarp Kamishibai), in the stage's variable pane. The table takes the heading the extension gives, and shows values only while the debugger has paused the project |
| `./sprite-clone-inspector` | `SpriteClonePagination` chooses a running clone to show in Properties and Variables: number buttons for up to five clones, arrows and a number menu for more. When clones hold a name in the sprite variable `actorName` (TurboWarp Kamishibai plays several actors as clones of one sprite and tells them apart by it), an actor name menu replaces the numbers. Clones sharing a name get their clone number. `SpriteCloneVariables` shows and edits the chosen clone's values |
| `./block-image` | `createBlockImageRenderer` draws one block of any target as Scratch shows it. The editor only renders the target it edits, so the block is drawn in an off-screen workspace and a copy is returned. The editor passes its ScratchBlocks; this package does not import it. `BlockImage` places the drawing in a pane and falls back to the block's name in words. `hatName` names a hat. The temporary variable tables and the message pane's receiving hats and script starts use it |
| `./script-start` | `scriptStartOf` and `describeScriptStart` tell how the script holding a block starts: a hat, a function (custom block definition) or a named function of TurboWarp Plus. The senders of the message diagram and the temporary variable tables use it |
| `./native-tile-title` | `observeTileNameTitles` gives each tile of the GUI's sprite list a tooltip with its full name, also when the list replaces its tiles later |

Each pane with a stylesheet exports it as `<pane>.css`. Load it as a global stylesheet. Labels are in English, or in Japanese when `locale` starts with `ja`.

Reading messages and editing variables come from `@kubohiroya/turbowarp-plus-editor-project-model`, so these panes and the Editor's project search judge a project the same way.

React 16.14 or later is supported, because the Editor mounts these panes in the GUI's React 16.

## Verification

Run `npm test` to build the package, check that it uses no React API newer than 16.14, and test the message pane and the sprite info adapter. Run `npm run test:browser` to drive the asset pane, the properties form and the toolbar in Chromium.

`.github/workflows/release.yml` publishes to npm when the version in `package.json` is not on npm yet, after the tests pass. It authenticates with npm's trusted publisher (OIDC), so npm's configuration records this workflow's filename.

## License

MPL-2.0. These panes were split out of `@kubohiroya/turbowarp-plus-editor-layout`, whose history this repository keeps. The properties form came from the previous sprite properties source at `80825f7`. They carry no GPL code and import no GPL module.

The existing `readTargetFunctions(target, {others, describeScript})` API still returns `messageGraph` from the shared message scanner. Hosts without `scriptRelations` can render this data, opening ordinary scripts through `onOpenScript` with their original `id` and `targetId`, and foreign functions through `onOpenFunction` with `owner`. The legacy `showCalls` and `showMessages` settings hide arrows without changing node positions or zoom; wire the new rail controls to `relationVisibility`. Missing visibility settings default to visible. Foreign function arrows show the function name, while their destination nodes show only the sprite name or stage. No project migration is required; roll back by restoring the host's previous package pin and rebuilding.

Supply `readTargetFunctions` with `getTargetThumbnail(targetId)` to put the owner's current costume or backdrop before its name. The URL is stored in `GlobalFunctionOwner.thumbnailUrl`; hosts without a thumbnail keep the text-only node.

Ordinary relationship nodes put the full hat or function name above the target name. Long names wrap, expanding the diagram’s shared node height; endpoints, labels, the minimap, and drag bounds follow that height. Foreign function nodes retain only their thumbnail and target name. Arrow labels omit repeated target names and keep just function or message names without hourglass icons. Waiting sends keep the 7/5 dash pattern; ordinary sends use 3.5/2.5 dashes. Both modes have separate paths when they connect the same nodes, including in the minimap.
